## 【改良版】ローカルAIとローカルSQLサーバーにフィボナッチ忘却を実装　　ー　公開ノート

---

## 研究には「忘れ方」が必要だった

前回、『ローカルAIとローカルSQLサーバーにフィボナッチ忘却を実装　　ー　公開ノート　ー』
https://zenn.dev/morc_b13/articles/a57344276ef637
を書いたが、handoverフォルダーに引継書を放り込んでおいただけで、私自身も使い方を忘れていた。

それは、ClaudeやChatGPTなどのAI自身が過去の記録を自分で検索できるようになったことが大きい。しかし、v51 から v175 まで、百数十本たまった引継書を全部保持しているわけではない。

**研究は時系列に意味がある**。関連性だけで探す通常の検索に対して、研究の記憶では「いつ確定したか」「どちらが後の判断か」がそれ自体情報だ。関連度が同点なら、新しい判断が古い判断を上書きしていなければならない。

必要なのは「全部覚える」でも「直近だけ覚える」でもない、**忘れ方の設計**だった。

そこで、研究対象そのものであるフィボナッチ数列に、記憶の管理をやらせることにした。

## 原理：保持インデックスは 0, 1, 2, 3, 5, 8, 13, 21, …

引継書を新しい順に並べ、インデックスがフィボナッチ数(と0)のものだけを「想起対象」とする。

| tier | 新しい方から | 実際の版 |
|---|---|---|
| 0 | 0番目 | v175(円錐曲線幾何) |
| 1 | 1番目 | v174(光学ノード) |
| 2 | 2番目 | v173(方針転換) |
| 3 | 3番目 | v172 |
| 4 | 5番目 | v169 |
| 5 | 8番目 | v161 |
| 6 | 13番目 | v160 |
| 7 | 21番目 | v145 |
| 8 | 34番目 | v128 |
| 9 | 55番目 | v104 |

直近は毎回、少し前は飛び飛び、遠い過去はランドマークだけ。78件の引継書が10件に圧縮される。

この方式を選んだ本当の理由は、美しさではなくスケーラビリティだ。**保持数は件数に対して対数的にしか増えない**。フィボナッチ数の逆関数は対数なので、引継書が100件でも保持は約11件、1000件でも約16件。研究が何年続いても、ローカルLLMの小さなコンテキストに収まり続ける。「長期研究でも破綻しない」──これが設計の第一条件で、フィボナッチはその条件を最小の規則で満たす解だった。

さらにオプションで、tier が1つ深くなるごとに検索の関連度スコアへ **1/φ ≈ 0.618** を掛ける。tier4 で重みは約 0.15、tier7 で約 0.03。古い記憶は「強く関連するときだけ」浮上する。減衰率に黄金比を使うのは半分は洒落だが、半分は本気だ──保持間隔がフィボナッチなら、減衰もその特性方程式の根に従うのが筋だろう。もっとも、これは実用条件を満たした後のご褒美である。

大事な設計判断が一つ。**忘却とは削除ではない。想起密度を落とすことである。** 全文検索(`--search`)は常に全件を対象にする。消えるのは記録ではなく、想起の密度だけだ。人間だって日記は捨てていない。繰らなくなるだけで。

## 構成：ぞうさん＋elyza＋足し算的スコアリング

```
新引継書 ──→ 登録 (版番号自動抽出・重複チェック・冪等)
                          │
                          ▼
        PostgreSQL: handover(記憶) + knowledge(書庫)
                          │ ←── フィボナッチ選別 (--fib)
                          ▼
        チャンク分割 → キーワード＋文字バイグラムでスコアリング
                          │ ←── 黄金比減衰 (--decay)
                          ▼
        上位チャンク(予算6000字) ──→ Ollama (elyza 8B) ──→ 出典つき回答
```

- **DB**: PostgreSQL(ぞうさん)。`handover` テーブルに版番号・本文・日付。
- **LLM**: Ollama 上の日本語8Bモデル(llama-3-elyza-jp-8b)。完全ローカル。
- **検索**: 埋め込みベクトルではなく、キーワード＋文字バイグラムの表層一致。枯れた方式だが、依存が少なく、なぜそのチャンクが選ばれたかが目で追える。スコアは一致の**足し算**で決まる──このシステムの中でも Nature knows only addition だ。
- **二層構造**: 引継書(`handover`)はフィボナッチ忘却の対象。Zenn記事や会話ログは `knowledge`(書庫)という別テーブルに入れ、忘却の対象外とする。机の上のノートは古びるが、書棚の蔵書は古びない。

## 現実は汚い：151ファイルとの格闘

理屈は美しいが、現実のフォルダはこうだった。

- ファイル151本。引継書、Zenn記事の下書き、README×7、書籍の章、理論構想書が混在
- 命名規則は `handover_v105.md`、`引継書_v118.md`、`B13_v133_hikitsugi.md`、`Claude-2026-03-28-v80.md` と全部バラバラ
- 同じ版のコピーが `(1)` 付きで複数
- おまけに過去の一括投入の失敗で、DBには「version=ファイル名、日付=全件同時刻」という91件の残骸

最後のが致命的だった。日付が全件同じだと、フィボナッチ忘却の階層が意味をなさない。実際、tier0(最新の記憶)がZennノートになっていた。

対処として一括登録ツールに入れたのは:

1. **引継書パターンフィルタ**──ファイル名に handover/引継/hikitsugi 等を含むものだけ対象。記事やREADMEは自動除外
2. **版番号はファイル名からのみ抽出**──本文中の偶然の「v1」を拾わない
3. **同版の優先採用**──`handover_v104.md` > `chatgpt_brief_v104.md` の優先順位で1本だけ
4. **created_at にはファイルのmtime**──執筆順がそのまま忘却の階層になる
5. **冪等性**──何度実行しても登録済みはスキップ。新しい引継書を書いたらフォルダに置いて同じコマンドを打つだけ

テーブルを一度まっさらにして再登録した結果、v51〜v175の78件が正しい時系列で入り、フィボナッチの階層が初めて本物の研究史の上に載った。

```bash
$ python3 b13_local.py --version --fib
フィボナッチ忘却: 78件中 10件を想起対象に保持
```

## 評価：忘却のコストが早速見えた

「BpVMの進行状況は?」と訊いてみた。返ってきた出典は tier1(v174)、tier2(v173)、tier3(v172)、tier7(v145)。内容は──BpVMの三値判定(FORWARD/BLIND/ABSTAIN)の規律が光学ノードへ移植されつつあること、公理と写像の分離、スコープの確定。**現在の輪郭としては正しい**。

しかし、BpVMの進行が最も濃く記録されているはずの回──実データ初走行で全BLINDを正直に記録した引継書──は出てこなかった。保持一覧と突き合わせると、その時期の版はちょうど forget 階層に落ちていた。検索の失敗ではない。忘却システムが設計どおりに忘れた結果だ。

面白いのは、それでも答えの方向は合っていたことだ。細部は忘れても、方針は覚えている。ランドマークだけ残した記憶は、人間の記憶とよく似た振る舞いをする。

関連度スコアが最大6.0と低めに出たのも、悪くない性質だと思っている。「保持している記憶の中に強い一致はない」という正直なシグナルとして読めるからだ。過去を掘りたければ `--fib` を外して全件検索すればいい。忘れたことと、思い出せることの間に、明示的なコマンドの一手間がある──この摩擦は残しておきたい。

## 限界と今後

正直に書いておく。

- 検索は表層一致であり、意味検索ではない。「黄金比」と「φ」は自動では結ばれない(質問に併記すれば拾える)
- 8Bモデルは資料があっても混同する。回答は「索引つき下書き」として扱い、確定判断は根拠チャンクの目視かクラウド側での検証に回す
- 想起フォールバック(フィボナッチ記憶で薄かったら自動で全件検索に切り替える)は実装候補だが、まだ入れていない。「忘れたものは忘れたまま」の思想と、利便性のどちらを取るか迷っている

それでも、百数十本の研究史がローカルで、φの秩序で想起できるようになった。フィボナッチ数列を研究してきた枠組みが、自分の記憶の管理をフィボナッチ数列に任せる──この再帰は、悪くない気分だ。
